# Known limitations

Acknowledged, out of scope for now. Found during an adversarial audit of the finished build. Numbered L2 through L6 to match that audit's own report; L1 (no `#![forbid(unsafe_code)]` on the `fuzz` and `benches` crates) is not listed here because it was closed rather than documented: both crates carried no unsafe code already, so the attribute was added and both were confirmed to still build.

- L2: the fill-or-kill dry run's read-only counting pass in the reference engine uses `OrderId::MAX` as a sentinel taker id, and `u64::MAX` is a legal client-supplied order id. Harmless today, since the dry run's events are discarded and nothing keys off the sentinel id itself, but a latent trap if a future change ever inspects those events before discarding them.
- L3: both engines' replay digest uses `std::collections::hash_map::DefaultHasher`, confirmed stable across three separate processes in the same build (and, found along the way, the two engines produce equal digests for the same book, a stronger property than either was required to have). The standard library reserves the right to change this algorithm between Rust releases, so digest stability is a per-toolchain guarantee, not an archival one.
- L4: the reference engine's own command log grows unbounded by design, roughly 3.2 gigabytes at 100,000,000 commands. Acceptable for a test oracle that carries no zero-allocation claim (see FINDINGS.md's note on why), but the bound on how long a single `RefBook` can usefully run is stated nowhere.
- L5: the fuzz generator's `Stats` counters print their per-reject-reason and per-kind breakdowns via `HashMap`, whose iteration order is not guaranteed stable between runs even when every count is identical. Purely cosmetic, but it makes diffing two runs' reported output noisier than it needs to be.
- L6: the generator's amend-targeting logic falls back, 5 percent of the time, to a fabricated resting-order view (a placeholder remaining quantity and price) when it chooses not to target a real live order. When the randomly chosen id happens to actually be live, the quantity and price deltas computed from that fabricated view do not reflect the real order's actual state. A distribution-intent nit with no correctness impact, since the command sent is still valid input either way.
- The event auditor's per-order tracking map never evicts an entry; nothing in the auditor itself bounds how many distinct order ids it can accumulate over a run. In practice this stays small because the fuzz generator's own id pool is bounded and ids cycle through it, but that bound belongs to the generator, not to the auditor, and is not enforced by the type that depends on it. Noted directly in the auditor's own source as well.
